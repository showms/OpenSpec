## Context

Project configuration selects its default workflow with the `schema` key. The `schema init --default` path instead writes `defaultSchema`, a field that no project-config reader consumes, while still reporting success. The same block hardcodes `openspec/config.yaml` and parses/stringifies existing YAML as a plain object, so it can bypass an existing `config.yml` and discard comments.

The project already exposes `resolveConfigFilePath()` with the same `config.yaml`-then-`config.yml` precedence used by configuration readers, and the existing `yaml` dependency provides a document API that retains comments while changing individual mapping entries.

## Goals / Non-Goals

**Goals:**

- Make both flagged and interactive default selection persist through the canonical `schema` key.
- Update the same config file that project commands will subsequently read on macOS, Linux, and Windows.
- Preserve unrelated mappings and comments in an existing project config.
- Repair stale `defaultSchema` output when the command next updates the default.
- Prove that the configured schema is effective for subsequent change creation.

**Non-Goals:**

- Automatically migrate every repository that previously ran the broken command.
- Change project-config precedence or introduce a second accepted default-schema key.
- Guarantee rollback across schema and config files after an operating-system write failure.
- Change `--no-default`, prompting defaults, or general schema-generation behavior.

## Decisions

### Use the canonical project-config field

The update will set the root `schema` mapping entry to the initialized schema name and remove a root `defaultSchema` entry if present. The CLI will not teach configuration readers to accept `defaultSchema`: keeping one canonical persisted field avoids permanent ambiguity and matches every other project-config producer and consumer.

Alternative considered: read `defaultSchema` as a compatibility alias. This would leave configurations containing both keys with unclear precedence and would not reliably repair projects where the old `schema` value remains alongside the inert key.

### Resolve the existing config filename through the shared lookup

The command will use `resolveConfigFilePath(projectRoot)` and update its result. Only when neither supported file exists will it create `openspec/config.yaml`. All paths will continue to be constructed with `path.join()`.

Alternative considered: continue writing only `config.yaml`. Because config loading prefers that filename, creating it beside `config.yml` would shadow the user's existing schema, context, rules, references, and store declarations.

### Modify YAML as a document

For an existing config, the command will parse a YAML document, verify that it is a mapping, set `schema`, remove `defaultSchema`, and serialize the document. This preserves comments and unrelated entries better than converting the document to a plain JavaScript object.

For a missing config, the command will create the minimal canonical mapping containing `schema`. Full cross-file transactional ordering and rollback remain out of scope so this change does not overlap the separate schema replacement validation fix.

Alternative considered: parse and stringify a plain object after renaming the key. That is the smallest code change, but it retains the existing comment loss and alternate-filename bug.

### Test observable configuration and downstream resolution

Command-level tests will cover configs that are missing, named `config.yaml`, and named `config.yml`. Assertions will verify the persisted mapping, preservation of unrelated content and comments, removal of the obsolete key, and schema selection by subsequent change creation. Existing `--no-default` behavior remains covered as a non-mutation contract.

## Risks / Trade-offs

- **YAML serialization can normalize minor formatting around an edited node** → Use the document API, assert comment and field preservation, and avoid rebuilding the whole config object.
- **Removing `defaultSchema` could delete an unknown user-defined field with that name** → The field was generated by this command and has never been part of the valid project-config contract; cleanup only occurs when the user explicitly asks the command to set a default.
- **A low-level write failure can still leave schema and config updates out of sync** → Keep this limitation explicit and avoid claiming full transactionality in this change.

## Migration Plan

No automatic migration is required. New invocations write the correct field, and rerunning `schema init <name> --force --default` on an affected schema repairs the config and removes the obsolete field. Reverting the code restores the previous command implementation without changing project-config readers.
